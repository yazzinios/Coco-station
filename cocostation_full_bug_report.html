CRITICALasyncio.get_event_loop() crashes on Python 3.12
auth_routes.py (×14 calls) · rbac.py (×8 calls)
asyncio.get_event_loop() raises RuntimeError: There is no current event loop on Python 3.12+ when called from a thread that doesn't own a running loop. Every auth endpoint, every RBAC endpoint, and every LDAP operation uses this pattern. On Python 3.12 the entire auth system would stop working.
Fix: Replace every asyncio.get_event_loop() with asyncio.get_running_loop(). Already done correctly in main.py — apply the same pattern to both files.
CRITICALDJ stream/detected and stream/ended have no IP allowlist
dj_routes.py · mediamtx.yml
Both MediaMTX webhook endpoints (POST /api/dj/stream/detected and stream/ended) are completely unauthenticated AND publicly reachable. Anyone who sends a POST to these endpoints can instantly trigger a "DJ is live" sequence — fading out all music, switching all decks to an empty stream.
Fix: Add an IP allowlist check: only accept requests from 10.20.0.2 (MediaMTX container). Add a FastAPI dependency: if request.client.host != "10.20.0.2": raise HTTPException(403). Or add a shared secret header in MediaMTX's runOnReady curl and check it server-side.
CRITICALTrigger lock never released if mic_open_sequence raises after acquire
announcement_engine.py · main.py — mic_on
In mic_open_sequence() the lock is acquired with await _TRIGGER_LOCK.acquire(). The try/except does release the lock on error — however if the error occurs BEFORE the try block (e.g. during _mic_duck_pct()), or if mic_close_sequence() is never called because the client disconnects silently, the lock stays held forever. The station freezes: no more announcements, no more scheduled plays, nothing goes through the trigger lock again until a manual reset API call.
Fix: In mic_on endpoint (main.py), wrap the entire flow in a try/finally that calls fade_restore_after_mic() and forcibly releases the lock if it's still held. Also add a watchdog: if the mic is still "active" after session_hours * 60 minutes, auto-call mic_off.
CRITICALLISTENER_HISTORY lost on every container restart
main.py — _record_listener / LISTENER_HISTORY
The entire RTSP connection history is in a plain Python dict. Every restart wipes it. Given nightly restarts or deploys, the analytics history page is always empty. Already flagged in the security report — still not fixed.
Fix: On startup, load from a listener_history DB table. Flush to DB every 5 minutes via a background task. Same pattern used for music_requests already.

HIGH_scheduler_owner tag never re-stamped on track_ended advances
main.py — track_ended · scheduler.py — _trigger_recurring_mixer_schedule
When a playlist advances via track_ended, the new track starts without _scheduler_owner being set. The mixer stop job's fallback logic (last_run_date) was patched but the root cause remains — ownership is only ever set in _trigger_recurring_mixer_schedule on first play, not on subsequent advances.
Fix: In track_ended (main.py), after setting the new track, check if the deck has an active scheduler context and re-stamp the owner. Or, in _trigger_recurring_mixer_schedule, add a hook that persists the owner ID through all track_ended callbacks for that deck.
HIGHDJ announce endpoint uses hardcoded 6-second sleep for file playback
dj_routes.py — dj_announce
When a DJ plays a pre-recorded file announcement, the code does await asyncio.sleep(6) regardless of the actual file duration. A 30-second announcement file would restore volume after 6 seconds while the file is still playing. The TTS path correctly uses audio_dur_fn to get the real duration — the file path does not.
Fix: Use _audio_dur_fn to measure the file duration before sleeping. Same pattern as the TTS branch directly below it in the same function.
HIGHDuck engine refcount mismatch when announcement fails mid-sequence
announcement_engine.py — play_announcement_sequence
If the sequence raises an exception between the fade-down and the fade-up, the finally block correctly fades back up. However, _DUCK_REFCOUNT_REF in main.py (the separate ducking engine) is not decremented. On the next announcement the engine thinks ducking is already active and skips the fade-down, leaving music permanently at duck level.
Fix: The announcement engine and the main.py duck engine are two separate systems that both touch volume. They need to be unified — or play_announcement_sequence should always call _duck_release() on any exit path, not just manage volumes directly.
HIGHRedis connection singleton is never closed or reconnected on failure
dj_redis.py — get_redis
The module-level _redis singleton is created once and reused forever. If Redis drops and reconnects, the stale client object may be in a broken state — all subsequent calls silently fail with no reconnection attempt. A Redis restart during a DJ session would freeze the entire DJ engine.
Fix: Add error handling: catch redis.exceptions.ConnectionError in each call site, reset _redis = None, and retry once. Or use aioredis.from_url(..., retry_on_error=[redis.exceptions.ConnectionError]).
HIGHTTS files accumulate in /announcements with no cleanup
tts.py · main.py — create_tts_announcement
Every TTS call generates a new tts_<uuid>.mp3 file. These are never deleted — not when the announcement is deleted, not on restart. Over time (especially with recurring schedules that auto-play TTS) the announcements volume fills up, and eventually ffmpeg fails to write new files.
Fix: In delete_announcement, also unlink the file from ANNOUNCEMENTS_DIR if the type is TTS. Already done for MP3 uploads — apply the same logic to TTS. Also add a startup sweep that removes orphaned TTS files not referenced by any announcement in the DB.
HIGHHeartbeat runs while decks dict may not be initialised
scheduler.py — _ap_heartbeat / _ap_check_oneoffs
The scheduler starts 10 seconds after startup and begins calling _ap_check_oneoffs and _ap_heartbeat. Both functions access _state["announcements"] and _state["music_schedules"] directly. If the DB is slow and init_scheduler is called before those lists are populated (they default to empty lists only if the DB succeeds), a KeyError or empty list causes the first few poll cycles to silently miss due triggers.
Fix: Guard all _state accesses with .get(key, []) defaults. Already done in some places — apply consistently throughout the heartbeat and oneoff checker.
HIGHupdate_last_login fails silently — users table missing last_login column
db_auth_helpers.py — update_last_login · migrate.py
Every login calls UPDATE users SET last_login = NOW(), but the last_login column is never created in BASE_SCHEMA_SQL or any migration. The UPDATE silently fails on every login with a psycopg2 error caught and swallowed. The column simply doesn't exist.
Fix: Add to the REPAIR_SQL block in migrate.py: IF NOT EXISTS (SELECT 1 FROM information_schema.columns WHERE table_name='users' AND column_name='last_login') THEN ALTER TABLE users ADD COLUMN last_login TIMESTAMP WITH TIME ZONE; END IF;

MEDIUMRecurringMixerScheduleCreateRequest.model_post_init uses wrong hook name
schemas.py
The model uses model_post_init(self, __context) which is a Pydantic v2 hook. The project appears to use Pydantic v1-style validation elsewhere (BaseModel without model_config). If the version is v1, this hook is silently ignored — stop_time="" is never coerced to None, and the DB stores an empty string that later reads as a truthy stop_time.
Fix: Use a Pydantic v1 validator: @validator('stop_time', always=True) def _coerce_stop_time(cls, v): return None if v == '' else v. Or confirm Pydantic v2 is installed and model_post_init is actually firing.
MEDIUMDJ deck auto-expire on RESERVED status can stop a live stream
dj_redis.py — reserve_deck
await r.expire(_k_deck(deck_id), RESERVE_TTL) sets a 120-second TTL on the deck hash. But set_stream_detected calls await r.persist(_k_deck(deck_id)) to remove it. If the stream takes more than 2 minutes to connect (slow OBS start, network delay), the deck key expires and reverts to AVAILABLE — then another DJ could reserve the same deck mid-stream.
Fix: Increase RESERVE_TTL to at least 300 seconds, or track reservation time separately from the deck key TTL.
MEDIUMOne-off announcement checker fires the same announcement multiple times
scheduler.py — _ap_check_oneoffs
The checker runs every 10 seconds. It sets ann["status"] = "Played" in memory then fires an async task. If the DB update_announcement_status is slow (takes >10s), the next poll cycle sees the in-memory status already as "Played" — but if the API container restarts between the status set and the DB write, the announcement fires again on the next boot.
Fix: Write the status to DB first (synchronously, not as a background task) before firing the play task. This is more critical for one-offs than for recurring — the current order should be reversed.
MEDIUMTTS path uses /app/data/announcements — fails outside Docker
tts.py
TTS_DIR = "/app/data/announcements" is hardcoded to the Docker container path. Running the API locally (dev mode, without Docker) creates files in the wrong place and the ANNOUNCEMENTS_DIR path in main.py (data/announcements relative) points somewhere else. The announcement engine then can't find the TTS file.
Fix: Use the same env-driven path: TTS_DIR = os.getenv("ANNOUNCEMENTS_DIR", "/app/data/announcements"). Or import the path from main.py's ANNOUNCEMENTS_DIR constant.
MEDIUMDeck F missing from DB seed — all schedule/mixer operations skip it
migrate.py — BASE_SCHEMA_SQL
The INSERT INTO decks seed and the INSERT INTO deck_names seed both only insert decks a–e. Deck F is defined in DECKS in main.py and works at runtime, but any DB query that joins on the decks table (e.g. foreign key checks) will fail for deck F. This also means deck F's name is never persisted.
Fix: Add ('f', 'Deck F', 100, false) to both INSERT statements in migrate.py and add to the REPAIR_SQL block: INSERT INTO decks (id, name, volume, is_playing) VALUES ('f','Deck F',100,false) ON CONFLICT (id) DO NOTHING;
MEDIUMmulti_tracks field ignored in RecurringScheduleCreateRequest
schemas.py · main.py — create_recurring_schedule
RecurringScheduleCreateRequest includes a multi_tracks field, but the schedule dict built in create_recurring_schedule in main.py never includes it. The field is accepted by the API but silently dropped — any multi-track announcement schedule created via the UI loses its track list.
Fix: Add "multi_tracks": req.multi_tracks to the schedule dict in create_recurring_schedule and update_recurring_schedule, and ensure db.save_recurring_schedule persists it.
MEDIUMAppContext.jsx WS reconnect fires even after logout
dashboard/src/context/AppContext.jsx
The connectWS function checks the destroyed flag at the start, but destroyed is set in the cleanup closure from useEffect. On logout, setCurrentUser(null) triggers a re-render before the cleanup runs. The WS close in the logout callback fires after the new render has already scheduled a new useEffect — creating a brief window where a new WS connection opens for a null user, gets a 4001 close, and calls logout() again.
Fix: In the logout callback, set a module-level "logging out" flag that connectWS checks before opening. Or move the WS close into the useEffect cleanup only, not in logout directly.
MEDIUM_play_content uses local path fallback that silently returns 60s timeout
announcement_engine.py — _play_content
The duration lookup tries data/announcements/{filename} and /app/data/announcements/{filename}. If neither exists (e.g. the file was deleted between upload and playback), it falls back to content_duration = 60.0 and proceeds — sending the play command for a missing file and then waiting 70 seconds for an announcement_ended event that will never come.
Fix: Check if the mixer-side path file exists before sending the play command. If it doesn't, log an error and return early — don't send the play command and wait 70 seconds.

LOWDeckState schema missing is_crossfading field
schemas.py
The DeckState Pydantic model doesn't include is_crossfading, but the runtime DECKS dict uses it. Not a crash — FastAPI just won't validate it — but if a response ever uses the DeckState model directly the field would be dropped.
Fix: Add is_crossfading: bool = False to DeckState in schemas.py.
LOWAnnouncement content duration lookup not cached
announcement_engine.py — _play_content · main.py — get_audio_duration
Every announcement playback calls ffprobe to measure duration. For recurring announcements that play every 30 minutes this is a fresh subprocess call every time. Not a crash, just unnecessary overhead — especially on a Raspberry Pi or low-spec server.
Fix: Cache durations in a module-level dict keyed by file path + mtime. Invalidate on mtime change.
LOWScheduler heartbeat logs "next" times using future-next-day calculation
scheduler.py — _ap_heartbeat
When a recurring schedule has already run today, _get_seconds_until_hhmm adds a full day and reports "in 23h 45m" in the heartbeat. The log says "Recurring: Greeting Ghita AR in 23h 45m" right after it just ran, which is technically correct but visually confusing — looks like it failed.
Fix: Skip the "upcoming" entry for schedules whose last_run_date == today_str, or add "(ran today)" suffix to the label.
LOWLibrary file serve endpoint has no Content-Disposition or Range support
main.py — GET /api/library/file/{filename}
The file serve endpoint uses FileResponse without content_disposition_type or HTTP Range support. Browsers that request audio files with Range: bytes=... (e.g. seeking in the request page audio preview) receive a 200 with the full file instead of a 206 partial — breaking seek in the public request page's audio preview player.
Fix: FastAPI's FileResponse does support Range requests natively — just ensure media_type is set correctly per file extension rather than always "audio/mpeg".
